# Авторизация в приложении: что сделано и что осталось

## 1. Как запускать

Порт обязательно **3000** — именно он прописан в настройках Supabase и Google.

```
flutter run -d web-server --web-port 3000 --web-hostname 0.0.0.0
```

Потом открыть в браузере `http://localhost:3000`.

> Почему `--web-hostname 0.0.0.0`: при значении по умолчанию сервер слушает
> только IPv6, и браузер в него не попадает — страница не открывается.
>
> **Это и была причина, по которой «кнопка Google не грузилась».**
> Сами настройки Google, Supabase и Google Cloud были верные — приложение
> просто запускалось не на том адресе (или на Windows-десктопе, где возврата
> из браузера вообще не происходит).

## 2. Структура проекта

В `lib` семь файлов, каждый отвечает за одно:

| Файл | За что отвечает |
|---|---|
| `main.dart` | Запуск, подключение Supabase и Firebase, нижнее меню из двух вкладок |
| `ui_kit.dart` | **Общие** виджеты: экран входа, экран после входа, форма, таблица |
| `supabase_tab.dart` | Вкладка Supabase: своя авторизация, свой `select`/`insert` |
| `firebase_tab.dart` | Вкладка Firebase: своя авторизация, свой `onValue`/`push` |
| `social_oauth.dart` | Прямой OAuth для ВК и Яндекса |
| `oauth_window_web.dart` / `oauth_window_io.dart` | Окно входа ВК и Яндекса: версия для браузера и для телефона, нужная подставляется при сборке |
| `firebase_options.dart` | Ключи Firebase (сгенерированы FlutterFire) |

Старый `users_widgets.dart` удалён — его заменил `ui_kit.dart`.

Главное упрощение: **экран входа и экран после входа теперь одни на обе
вкладки**. Вкладка просто передаёт в них свои функции («как войти», «как
прочитать список»). Раньше форма входа была написана дважды.

Каждая вкладка по-прежнему полностью независима: своя база, своя сессия.
Можно войти в Supabase и не входить в Firebase — так и работает.

## 3а. Что ломалось по дороге

### GitHub во вкладке Firebase

Было две ошибки подряд.

**Первая — `incorrect_client_credentials`.** В Firebase попал секрет от
другого приложения GitHub: у `Flutter Lab Supabase Auth` и
`Flutter Lab Firebase Auth` секреты разные, а на вид одинаковые.
Решилось перегенерацией секрета у приложения `3997251`. Готово.

**Вторая — `account-exists-with-different-credential`.** Это уже не
поломка, а штатное поведение Firebase. В проекте уже есть пользователь
`hotfloe0410@gmail.com`, созданный входом через Google. GitHub приносит
тот же адрес почты, а Firebase по умолчанию не разрешает два аккаунта
на один адрес.

Решено одной настройкой (уже сделано):
[Firebase → Authentication → Настройки](https://console.firebase.google.com/project/flutter-app-982b4/authentication/settings)
→ «Привязка учётных записей пользователей» →
**«Создайте несколько учётных записей для каждого поставщика
идентификации»**.

После этого вход через GitHub заработал: в списке пользователей Firebase
появился второй аккаунт с тем же адресом почты — это и есть «GitHub-овский».

Firebase считает этот вариант менее строгим: на один адрес почты будет
два разных аккаунта. Для лабораторной это нормально и это самый простой
путь. «Правильная» альтернатива — связывать аккаунты в коде
(`linkWithCredential`): войти через Google, а потом привязать учётные
данные GitHub к тому же пользователю. Для демонстрации это лишнее
усложнение, но в отчёте упомянуть стоит.

### Яндекс во вкладке Firebase: `permission-denied at /Users`

Правила базы Firebase сейчас такие:

```json
{ "rules": { ".read": "auth != null", ".write": "auth != null" } }
```

Вход через Яндекс для Firebase чужой: Firebase о нём не знает, поэтому
`auth` пустой и список не читается.

В коде это уже исправлено: при входе через ВК или Яндекс приложение
дополнительно делает **анонимный вход в Firebase** — доступ к данным
появляется, а имя показывается настоящее, от Яндекса. Правила базы
при этом не трогаются.

Осталось включить сам способ входа:
[Firebase → Sign-in method](https://console.firebase.google.com/project/flutter-app-982b4/authentication/providers)
→ Add new provider → **Anonymous** → Enable → Save.

Честно про безопасность: включённый анонимный вход означает, что прочитать
базу сможет любой, кто знает публичный ключ приложения — то есть примерно
то же самое, что открытые правила. Для лабораторной это нормально (пароли
там и так лежат открытым текстом), но в реальном проекте так нельзя.
Если включать не хочется — альтернатива в том, чтобы убрать кнопки ВК
и Яндекса из вкладки Firebase и оставить их только в Supabase, где
у таблицы и так отключён RLS.

## 5. Важно про ВКонтакте

VK ID **не принимает адрес возврата по http** — при сохранении пишет
«Обязателен протокол https», и поле нельзя оставить пустым. Поэтому вход
через ВК принципиально не работает на `http://localhost:3000`, в отличие
от Google, GitHub и Яндекса.

В приложении ВК указан адрес `https://flutter-app-982b4.web.app/auth.html` —
это Firebase Hosting того же проекта, он бесплатный и сразу даёт HTTPS.
Чтобы вход через ВК заработал, приложение нужно один раз выложить:

```
flutter build web
firebase deploy --only hosting
```

Пока приложение открыто по http, кнопка ВК показывает понятное сообщение
об этом, а не непонятную ошибку от ВК. Адрес возврата код подставляет сам
из текущего адреса страницы, так что менять в нём ничего не нужно.

## 6. Как устроен вход через ВК и Яндекс

Их нет в списке провайдеров ни Supabase, ни Firebase — и преподаватель
отдельно оговорил «кроме вк и yandex». Поэтому с ними приложение работает
напрямую по OAuth 2.0:

1. Открывается окно входа сервиса (`oauth.yandex.ru` / `oauth.vk.com`).
2. Сервис возвращает пользователя на нашу страницу `web/auth.html`,
   дописав к адресу `#access_token=...`.
3. `auth.html` передаёт этот адрес обратно в приложение и закрывается.
4. Приложение достаёт токен и узнаёт имя:
   - у Яндекса — запросом к `login.yandex.ru/info`;
   - у ВК — прямо из адреса возврата, там уже есть почта и номер
     пользователя, лишний запрос не нужен.

Дальше показывается тот же экран: имя, список из базы и кнопка «Выйти».

### Про шаг 3 — что пришлось обойти

Обычно всплывающее окно отдаёт результат через `window.opener` — ссылку
на то окно, которое его открыло. С Яндексом и ВК это не работает: они
присылают заголовок `Cross-Origin-Opener-Policy`, и браузер намеренно
рвёт эту связь. Токен возвращался на `auth.html`, но до приложения
не доходил, и экран навсегда оставался в состоянии «Подождите...».

Поэтому результат передаётся через **BroadcastChannel** — это общий канал
для всех вкладок одного сайта, которому связь между окнами не нужна.
Код лежит в `lib/oauth_window_web.dart` (браузер) и
`lib/oauth_window_io.dart` (телефон); нужный файл подставляется при сборке.

## 5а. Имя пакета Android и сборка APK

Проект собирается в APK автоматически через `.github/workflows/main.yml`.
После подключения Firebase сборка один раз упала:

> Execution failed for task `:app:processReleaseGoogleServices`.

Плагин `google-services` сверяет `applicationId` из `build.gradle.kts`
с файлом `google-services.json`, а тот был выписан только на старое имя
пакета `com.example.my_first_flutter_app`.

Исправлено так: в проект Firebase добавлено второе Android-приложение
с пакетом `com.vottakaya.sobachka`, его клиент дописан в
`google-services.json`. Идентификаторы в `firebase_options.dart`
и `firebase.json` обновлены на новый.

То есть имя пакета осталось твоим, ничего откатывать не пришлось.

## 6а. Почему таблица Firebase загружается дольше, чем Supabase

Это не ошибка в коде, а расстояние до сервера. Замерила из браузера
время одного запроса, по четыре раза к каждой базе:

| База | Время ответа |
|---|---|
| Supabase | 107, 126, 119, 266 мс |
| Firebase Realtime Database | 1036, 1101, 1329, 919 мс |

Firebase отвечает примерно в восемь раз дольше. Причина в адресе базы:
`flutter-app-982b4-default-rtdb.firebaseio.com` — это регион США.
Supabase же стоит ближе.

Вдобавок Supabase делает **один** обычный запрос (`select` по HTTP),
а Firebase перед первой порцией данных успевает сделать несколько
обменов по веб-сокету: установить соединение, передать токен входа,
подписаться на изменения. Каждый обмен — примерно секунда, отсюда
и несколько секунд ожидания.

Что с этим сделано:

- Соединение с базой теперь открывается **заранее**, пока человек ещё
  вводит логин (чтение узла `.info/connected` в `initState`). Секунды
  на установку связи тратятся до входа, а не после него.
- Вместо пустого кружка показывается надпись «Подключаемся к базе
  Firebase...», чтобы не казалось, что приложение зависло.

Что можно сделать ещё, если захочется быстрее:

- Запускать сборку в режиме release: `flutter run -d chrome --release`.
  В обычном (debug) режиме Flutter отдаёт браузеру около тысячи
  отдельных JS-файлов, и само приложение стартует заметно медленнее.
- При создании базы выбрать регион поближе — у существующей базы регион
  сменить нельзя, пришлось бы создавать новую.

## 6б. Чего нет и почему

- **Apple** — убран по твоему решению. Для него нужен платный Apple Developer
  ($99/год), без него провайдер в Supabase и Firebase просто не включается.
  Если понадобится, кнопка добавляется одной строкой в список `social`
  в `supabase_tab.dart` и `firebase_tab.dart`.
- **Android не проверялся** — подключённых устройств и эмуляторов нет.
  Настройки для него в `AndroidManifest.xml` уже добавлены (возврат из
  браузера для Supabase и для ВК/Яндекса), но вживую это не запускалось.
- **Пароли в таблице `Users` хранятся открытым текстом** — так требует
  задание. В отчёте это стоит отметить как то, чего в реальных проектах
  делать нельзя.
