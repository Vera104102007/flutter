# Ответы на вопросы преподавателя

## 1. Как сделать роли в Supabase и Firebase

Главная мысль: **роль проверяется на стороне базы, а не в приложении.**
Спрятать кнопку мало — её видно через инструменты разработчика, и запрос
можно послать вручную. Поэтому в обоих случаях роль лежит в базе,
а правило «удалять может только администратор» записано там же.

### Supabase

Готовый SQL — в файле [`db/supabase_roles.sql`](db/supabase_roles.sql),
он уже выполнен в проекте.

- Таблица `profiles`: `id` (ссылка на `auth.users`), `email`, `role`
  (`user` или `admin`).
- Триггер `on_auth_user_created` создаёт строку профиля автоматически,
  когда человек регистрируется.
- RLS на `profiles`: пользователь видит только свою строку. Политик
  на запись нет вообще — поэтому выдать себе роль администратора
  из браузера невозможно, это делается только через SQL Editor.
- RLS на `Users`: читать и добавлять может кто угодно, а удалять —
  только тот, у кого в `profiles` роль `admin`.

**Проверено на живой базе, дважды:**

1. Вставила тестовую строку `_проверка_rls` и попробовала удалить её
   **без входа** — строка осталась на месте.
2. Зарегистрировала тестового пользователя `lab.test@example.com`,
   вошла под ним и повторила удаление **с настоящим токеном входа,
   но с ролью `user`** — строка снова осталась на месте.

В обоих случаях сервер отвечает `HTTP 204`, как будто всё прошло
успешно, но удалено ноль строк: RLS просто не показывает их запросу
на удаление. Это важная деталь — ошибки не будет, поэтому проверять
надо не код ответа, а то, что данные на месте.

А вот **с ролью `admin`** всё получилось: зашла в приложение под твоим
аккаунтом, нажала на корзину у строки `_проверка_rls`, подтвердила —
строка пропала и из таблицы, и из базы. Проверила запросом: её больше
нет. То есть политика работает в обе стороны, а не просто всё запрещает.

### Firebase

Правила — в файле [`db/firebase_rules.json`](db/firebase_rules.json).

- Ветка `profiles/{uid}` с полями `email`, `role`, `createdAt`.
- Правило на `Users/{запись}`: писать может любой вошедший, **а удалять
  (то есть записывать пустоту) — только если** в `profiles/{uid}/role`
  лежит `admin`.
- Правило на `profiles/{uid}`: человек может создать свой профиль, но
  только с ролью `user`, и не может потом эту роль поменять. Роль
  администратора выдаётся владельцем проекта.

Правила уже опубликованы, роль `admin` выдана обоим аккаунтам
`hotfloe0410@gmail.com` (их два — отдельно для Google и для GitHub,
см. пункт 2).

**Проверено на живой базе.** Вошла тестовым пользователем
`test.lab@example.com` с ролью `user` и попробовала три вещи:

| Действие | Результат |
|---|---|
| Прочитать список | `HTTP 200`, список пришёл |
| Добавить запись | `HTTP 200`, запись появилась |
| Удалить запись | `HTTP 401`, `"error": "Permission denied"` |

Запись после попытки удаления осталась на месте.

**Любопытная разница между платформами.** Firebase честно отвечает
ошибкой «Permission denied». Supabase же отвечает `HTTP 204`, как будто
всё прошло, но удаляет ноль строк — RLS просто не показывает запросу
те строки, которые трогать нельзя. То есть у Supabase проверять надо
не код ответа, а то, что данные на месте.

**Почему не custom claims.** «Правильный» способ ролей в Firebase — это
custom claims в токене. Но выставить их может только Admin SDK с сервера,
то есть нужны Cloud Functions, а они требуют платного плана Blaze.
У проекта план Spark, поэтому роль хранится в базе.

## 2. Что происходит при первом входе и при последующих

### Первый вход

- В разделе **Authentication появляется новый пользователь** с UID.
  Это и есть «регистрация»: отдельно регистрироваться не нужно, вход
  через Google или GitHub создаёт аккаунт сам.
- Supabase дополнительно создаёт запись в `auth.identities` — связку
  «аккаунт ↔ провайдер».
- Срабатывает триггер и появляется строка в `profiles` с ролью `user`.
- Отметки «когда создан» и «когда последний раз входил» совпадают.

### Последующие входы

- Новый пользователь **не создаётся**, UID остаётся прежним.
- Меняется только отметка последнего входа (`last_sign_in_at`
  у Supabase, `lastSignInTime` у Firebase).
- Выдаётся новая сессия и новый refresh-токен.
- В `profiles` не меняется ничего.

### Это измерено, а не взято из документации

Зарегистрировала тестового пользователя и сразу вошла под ним второй
раз. Вот что отдал Supabase:

| Когда | `created_at` | `last_sign_in_at` |
|---|---|---|
| Регистрация | `01:26:57.194` | `01:26:57.276` |
| Повторный вход | `01:26:57.194` | `01:27:14.514` |

Видно главное: при регистрации обе отметки совпадают с точностью
до долей секунды, при повторном входе `created_at` не изменился,
а `last_sign_in_at` сдвинулся на 17 секунд вперёд. Новой записи
в `auth.users` не появилось, в `profiles` тоже ничего не изменилось.

### Как это видно в приложении

Рядом с ролью показывается пометка **«Первый вход»**. Берётся она без
запросов к базе: и Supabase, и Firebase отдают у пользователя обе
отметки, и если они совпадают с точностью до нескольких секунд —
значит аккаунт только что создан.

### Отдельное наблюдение

Когда в Firebase включена настройка «несколько аккаунтов на один адрес»,
вход через другого провайдера с той же почтой создаёт **отдельный
аккаунт с новым UID**. Мы это видели своими глазами: после входа через
GitHub в списке пользователей появился второй `hotfloe0410@gmail.com`.
При настройке «объединять по адресу» вместо этого была ошибка
`account-exists-with-different-credential`.

## 3. Можно ли добавить картинки и файлы в Firebase

Да, для этого есть **Firebase Storage** (в Flutter — пакет
`firebase_storage`): файл кладётся в хранилище, обратно приходит ссылка,
её можно сохранить в базе рядом с записью.

**Но в нашем проекте хранилище пока не создано.** Я проверила запросом:
адрес `flutter-app-982b4.firebasestorage.app` отвечает `404 Not Found`,
то есть бакета нет. Чтобы он появился, нужно открыть раздел Storage
и нажать «Начать». Для проектов, созданных после осени 2024 года,
Google на этом шаге просит перейти на платный план Blaze с привязкой
карты — это стоит проверить на месте.

**Запасной вариант, который доступен уже сейчас:** хранилище Supabase.
Я проверила — его API отвечает на бесплатном плане (`HTTP 200`). Там
есть бесплатный лимит, и для лабораторной этого хватит.

## 4. Что нужно для авторизации через Apple

Коротко: **платный Apple Developer Program, 99 долларов в год.** Без него
провайдер Apple просто не включается ни в Supabase, ни в Firebase.

Что потребуется после оплаты:

1. **App ID** с включённой возможностью Sign In with Apple.
2. **Services ID** — отдельный идентификатор для входа с сайта
   и с Android, в нём прописываются разрешённые адреса возврата.
3. **Key (.p8)** — файл ключа, скачивается один раз. К нему нужны
   **Key ID** и **Team ID**.
4. В Firebase: вставить Services ID, Apple Team ID, Key ID и сам ключ.
   В Supabase: Client ID — это Services ID, а Secret — JWT, который
   собирается из `.p8`; он живёт максимум полгода и его надо
   перевыпускать.
5. Для настоящего iOS-приложения — ещё и галочка Sign in with Apple
   в Xcode, а значит компьютер с macOS.

Дополнительно: правила App Store требуют, чтобы приложение,
предлагающее вход через Google или другие соцсети, предлагало и вход
через Apple. То есть для публикации в App Store это не опция,
а обязанность.

Поэтому в приложении кнопки Apple нет — она была бы заведомо нерабочей.
Если аккаунт появится, кнопка добавляется одной строкой в список
`social` в `supabase_tab.dart` и `firebase_tab.dart`.

## 5. Сортировка и удаление в приложении

- **Сортировка:** в таблице нажатие на заголовок «Логин» или «Пароль»
  сортирует список, повторное нажатие меняет направление. Стрелка
  показывает текущий столбец. Работает на обеих вкладках.
- **Удаление:** кнопка с корзиной появляется в строке только
  у администратора. Перед удалением спрашивается подтверждение.
  Если кнопку всё-таки обойти, база откажет сама — см. пункт 1.

## 6. Что осталось сделать руками

1. **Проверить удаление на вкладке Firebase.** Запрет для обычного
   пользователя я проверила, а разрешение для администратора — нет:
   вкладка разлогинилась, а вход в твой аккаунт идёт через Google
   и GitHub, пароля у меня нет. Зайди и удали любую запись — роль
   `admin` тебе уже проставлена для обоих аккаунтов.
2. **Убрать тестовых пользователей**, которых я заводила для проверок:
   `lab.test@example.com` в Supabase (Authentication → Users)
   и `test.lab@example.com` в Firebase.
